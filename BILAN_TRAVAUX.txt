1.1  ROW LEVEL SECURITY (RLS) SUPABASE
---------------------------------------
Fichier créé : supabase/migrations/001_enable_rls.sql

Problème identifié :
  La table app_storage (unique table du projet) n'avait aucune
  protection RLS activée. N'importe qui possédant la clé anon
  publique (exposée dans le bundle JS) pouvait lire, écrire ou
  supprimer TOUTES les données de TOUS les coachs.

Ce qui a été fait :
  - Étape 1 : Création de la table app_storage si absente
      (colonnes : key TEXT PK, value TEXT, updated_at TIMESTAMPTZ)

  - Étape 2 : Ajout de la colonne coach_id UUID
      DEFAULT auth.uid() — Supabase renseigne automatiquement
      l'UUID du coach à chaque INSERT, sans modifier le code JS

  - Étape 3 : Instructions de back-fill (commentées dans le SQL)
      UPDATE app_storage SET coach_id = '<UUID>' WHERE coach_id IS NULL

  - Étape 4 : Index de performance sur coach_id

  - Étape 5 : ALTER TABLE app_storage ENABLE ROW LEVEL SECURITY

  - Étape 6 : 7 policies créées :
      Coach (rôle authenticated) :
        coach_select  → SELECT  si coach_id = auth.uid()
        coach_insert  → INSERT  si coach_id = auth.uid() ou NULL
        coach_update  → UPDATE  si coach_id = auth.uid()
        coach_delete  → DELETE  si coach_id = auth.uid()

      Étudiant (rôle anon) :
        student_read         → SELECT  sur clés "student:*" et "chat:*"
        student_chat_insert  → INSERT  sur clés "chat:*" uniquement
        student_chat_update  → UPDATE  sur clés "chat:*" uniquement

  Résultat :
    - Les namespaces "students:index", "gyms:index" et
      "planning:sessions" sont INVISIBLES au rôle anonyme
    - Un coach ne peut accéder qu'à ses propres données
    - Les étudiants peuvent lire leur fiche et écrire dans le chat

  ⚠️  CE FICHIER SQL DOIT ENCORE ÊTRE EXÉCUTÉ MANUELLEMENT
      dans le SQL Editor Supabase (voir Partie 2 — Reste à faire)

1.2  REMPLACEMENT DE Math.random()
------------------------------------
Fichier modifié : src/App.jsx (ligne 72)

Problème identifié :
  La fonction uid() utilisait Math.random() pour générer les IDs
  des étudiants. Math.random() n'est PAS cryptographiquement sécurisé
  et peut être prédit. L'ID étudiant figure dans le lien de portail,
  ce qui permettait une énumération potentielle.

Ce qui a été fait :
  AVANT : Math.random().toString(36).slice(2,10) + Date.now()...
  APRÈS : 8 octets via crypto.getRandomValues() → 16 chars hex

  Note : secureToken() (accessToken des étudiants) utilisait déjà
  crypto.randomUUID() et n'a pas été modifié.

  Nouveau namespace dans app_storage pour le profil coach.

  Chargement du profil au montage
    useEffect → safeGet(KEYS.coachProfile(uid)) → state coachProfile

    Décrémente (-1) à chaque suppression d'élève
    Met à jour le profil dans Supabase ET le state local

  onDeleted (StudentDetailPage)
    Mis à jour pour appeler updateStudentCount(-1) avant de recharger

  UpgradeModal
    Modal affiché quand la limite est atteinte :
      - Alerte rouge "limite de 3 élèves"
      - Prix 39€/mois avec sous-titre "Résiliation à tout moment"
      - Bouton "Passer à Pro — 39€/mois" → handleUpgrade()

  Badge plan dans la Sidebar
    "FREE" (gris) ou "PRO" (fond acid jaune) affiché à côté de
    "Studio Coaching" si le profil est chargé.

2.3  INTÉGRATION STRIPE CHECKOUT
----------------------------------

  api/create-checkout-session.js  (Vercel Serverless Function)
    Méthode : POST
    Entrée  : { coachId, email }
    Actions :
      - Crée une Stripe Checkout Session en mode "subscription"
      - Prix : STRIPE_PRICE_ID (variable d'env)
      - Metadata : { coachId } → utilisé par le webhook
      - success_url : {APP_URL}/#success
      - cancel_url  : {APP_URL}/#cancel
    Sortie  : { url } → le frontend redirige vers cette URL

  api/stripe-webhook.js  (Vercel Serverless Function)
    Méthode : POST (appelé par Stripe)
    Événement traité : checkout.session.completed
    Actions :
      - Vérifie la signature HMAC avec STRIPE_WEBHOOK_SECRET
        (sécurité : rejette toute requête non signée par Stripe)
      - Récupère coachId depuis session.metadata
      - Lit le profil coach dans Supabase via service key
      - Met à jour : plan → "pro", upgradedAt → timestamp ISO
    Note : bodyParser désactivé (config.api.bodyParser = false)
      car Stripe requiert le corps brut pour la vérification HMAC

  handleUpgrade() dans CoachApp_Inner
    Appelle /api/create-checkout-session en POST
    Redirige vers l'URL Stripe retournée
    Gestion d'erreur : alert si l'API ne répond pas

────────────────────────────────────────────────────────────────
ACTION 1 — Exécuter la migration RLS dans Supabase
────────────────────────────────────────────────────────────────
  STATUT : ⏳ EN ATTENTE

  Où : Supabase Dashboard → SQL Editor

  Quoi :
    1. Ouvrir le fichier supabase/migrations/001_enable_rls.sql
    2. Copier tout le contenu
    3. Coller dans le SQL Editor Supabase
    4. Cliquer "Run"

  Ensuite, back-fill des données existantes :
    a. Aller dans Supabase → Authentication → Users
    b. Copier l'UUID du coach (colonne "UID")
    c. Exécuter dans le SQL Editor :

       UPDATE app_storage
         SET coach_id = '<TON-UUID-ICI>'
         WHERE coach_id IS NULL;

    d. Vérifier : SELECT COUNT(*) FROM app_storage WHERE coach_id IS NULL;
       → doit retourner 0

  ⚠️  TANT QUE CETTE ÉTAPE N'EST PAS FAITE :
      - La RLS est absente, les données sont exposées
      - Après activation, les données sans coach_id seront invisibles
        (c'est pourquoi le back-fill est OBLIGATOIRE avant d'activer)
